# Receiver GPU常駐パイプライン

接線生成の追加方針は[Receiver接線計算の実装ハンドオフ](RECEIVER_TANGENT_HANDOFF.md)を参照。接線生成は現時点では未実装である。

## 目的・範囲

Receiverの復元頂点をGPUに保持し、差分復元→PTSに基づく補間→MeshRenderer描画を接続する。全頂点のreadback、CPU補間、毎描画時のMesh.vertices再転送を通常のGPU経路から除く。Sender、HTTP、GZip、配信形式（v1/v2）、楽曲分割は変更しない。旧VertexContainerのAPIは互換用に残す。

## データと責務

CPUは受信・展開、ヘッダー/範囲/重複/完全性検証、可変長キーフレームのタイル索引作成、シーケンス順、PTS、音声時計、ルート位置を扱う。GPUはキーフレームの量子化解除、3byte/頂点の差分展開、復元状態、再生待ちスナップショット、補間、必要な法線更新を扱う。全頂点を表すfloat配列は初期化とCPU経路だけで使用する。

キーフレームは元のバイト列とタイル記述子（開始頂点番号・頂点数・データ位置・タイル位置）を転送する。GPUは頂点ごとの所属タイルを二分探索し、Mesh別オフセットを用いて復元先と差分用の並び順を構築する。CPUで浮動小数の頂点コマンドへ展開しない。差分はパディング以外を変更せず転送し、GPUで符号付き二乗差分を加算する。

## バッファ・実行順

- 復元状態とpacked順→global頂点索引は永続GPUバッファ。
- 各スロットは入力バイト、タイル記述子、復元後スナップショット、完了確認を持つ。macOS/iOSではGraphicsFence（CPUSynchronisation / AllGPUOperations）、WebGPUではスナップショットの先頭16バイトだけを非同期readbackして完了を確認する。入力は完了まで書き換えない。
- 全処理をgraphics queueへ順序通りに投入する。非同期compute queueは使用しない。macOS/iOSでは次の復元投入にreadbackや前フレームのCPU完了通知は不要。WebGPUでは完了確認用の16バイトreadbackがスロット再利用条件になる。
- 完了状態を非ブロッキングで確認し、完了したスナップショットだけを音声同期のバッファ量に数える。
- 補間の読み出しは後続のスロット上書きより先に同じqueueへ投入する。表示用Meshバッファは復元状態から独立し、先読みで上書きされない。
- 入力/スナップショット用GPUプールは既定64MiB上限、最大64スロット。最低4スロットを確保できないモデルはCPUへフォールバック。実際のプール数はPTSバッファ上限+投入余裕8を目安に決める。Mesh描画バッファ・法線隣接情報等は別枠でモデルサイズに比例する。
- Updateあたり投入は最大8フレーム、CPU投入時間は約4msで打ち切る。GPU全体の実行時間上限を保証するものではない。

## 描画・法線・Bounds

初期化時だけMeshの頂点レイアウトをposition/normal/UVに構築し、Rawアクセス可能なGPU頂点バッファを取得する。三角形、submesh、UV、マテリアルは保持する。補間後の座標と法線をComputeShaderから直接書き込む。初期化後はCPUのMesh頂点変更APIを呼ばない。

法線設定はAuto/None/Recalculate。Autoは既知のUnlitだけ省略し、未知のシェーダーでは再計算する。Recalculateは補間後に面の外積を計算し、事前作成した頂点→隣接面索引を使って面積重み付き頂点法線を合成する。頂点ごとに一つのスレッドが書くのでfloat atomicは不要。縮退面・孤立頂点はゼロ法線を許容する。面の外積の二乗長がmax(1e-30, 1e-12×辺長二乗の積)以下なら丸め誤差として除外し、補間で潰れた面から不定方向の法線が出ることを防ぐ。元モデルの調整済み法線の復元、UV境界の頂点統合、接線再計算は対象外。法線マップ用接線は別途必要。

Boundsはキーフレームのタイル範囲からCPUで保守的に計算する。差分では最大絶対変位をCPUが圧縮バイトから求めて範囲を拡張する。再生時は前後スナップショットのBoundsを包含させる。GPU頂点をreadbackしてBoundsを求めない。

## 再生・回復

既存の音声主時計、最初のメッシュPTSへのseek、開始/再開余裕max(0.25秒,2フレーム)、再生中余裕0.05秒を維持する。デコード先読みは約0.5秒とし、消費済みスナップショットを解放してから補充する。GPU投入済みでも未完了のフレームは再生可能とはみなさない。表示待ちが満杯でPTS幅が不足する場合は中間スナップショットを解放し、最初の補間基点を保持して先へ進む。差分入力は飛ばさない。

Auto/GPU/CPUをReceiver Inspectorで選べる。法線設定とともに接続時に確定するため、変更後はReceiverを再接続する。Auto/GPUはComputeShaderと完了確認機能（macOS/iOSのGraphicsFence、WebGPUのAsyncGPUReadback）に対応する場合にGPUを試行する。GPU指定でも初期化失敗は警告を出してCPUへフォールバックする。GPU実行の例外時はCPU復元状態がないため、最後に表示済みの姿勢を保持して次のキーフレームからCPUで再開する。失敗した差分をCPUへそのまま適用しない。欠損・不正フレーム後もキーフレーム待ちとする。復帰キーフレームの先頭PTSが停止中の音声より後になる場合は、音声をそのPTSへシークして通常のプリロード条件で再開する。接続破棄時はプールとMeshのGPUハンドルを解放する。

## 検証と限界

1. 保存済みKAGURAデータのキーフレーム/連続差分をCPUとGPUで比較（検証専用readback）。許容絶対誤差1e-5。
2. 補間、Raw頂点出力、GPU法線、Bounds、UV/submesh維持を検証。法線の基準は面積重み付き定義としUnity実装とのビット一致は要求しない。
3. 不正・欠損入力、プール枯渇、PTSが公称より密な配信、再初期化とDisposeを確認。
4. macOS MetalとiPhone実機で60fps/300フレーム結合を確認。実測したdecode/描画/バッファ状態と未検証項目を記録する。

GPU内部の全頂点コピー・補間は残る。5秒結合による配信待ち時間も残る。GPUプール上限はCPU側の配信データを含まない。Receiverの先行ダウンロードは未復元フレームが結合数の2倍以上なら待機し、追加中の1チャンクを含め原則3チャンク未満に抑える（小さい結合数では最低16フレームを許容）。対応端末すべてで60fpsを保証するものではない。

## かくつき・配信競合への対応

- `.stmv` のGZip展開・フレーム分割をTask.Runで実行し、Unityスレッドでは全体の検証完了後にキューへ追加する。WebGLはスレッド制約により同期経路。不完全なチャンクを部分的に確定しない。
- プレイリスト取得コルーチンの重複起動を防ぎ、失敗したチャンクは最大3回再取得する。HTTP 200でもUnityWebRequestが失敗なら本文を採用しない。
- 再接続で破棄されたReceiverへHTTP完了通知が戻るNullReferenceExceptionを防止する。展開完了時にもDisposedを確認する。
- Senderはチャンク本体のアップロード完了後にstreaminfoを公開する。開発サーバーは同じディレクトリの一時ファイルからos.replaceし、GETは開いたファイルのfstatからContent-Lengthを取得する。音声playlistも同じ原子的更新を使う。
- 60fps時は完了済み＋投入中の管理上限40、GPUプール48スロット（48,482,688 bytes）。メモリ予算が小さいモデルでは上限を縮小する。
- 実機ログに5秒区間のfps、最長フレーム時間、未復元フレーム数を追加。平均fpsだけで短い停止が消えたとは判断しない。

テスト: `test_server_publication.py`（HTTP同時読み書き）、`verify_async_chunks.cs`（壊れた入力の原子的拒否・再試行・破棄後完了）、既存CPU/GPUテストが通過。更新後のGPU補充テストは40スナップショット上限・投入待ち最大8で通過。新しい実機ビルドでの測定結果は次項に記載。

### 残るモデルのかくつきと量子化誤差

実機の改善確認後、ユーザーから細かなモデルのかくつきが残るとの報告。2026-09-27の実行中Sender設定は60fps、subframesPerKeyframe=29、combinedFrames=300。音声時刻から毎更新のメッシュ提示時刻を求めており、ログの一致だけで元のモーションの正確さや量子化誤差まで検証できたことにはならない。

`DiffShader.compute`は元の前フレーム頂点をpreviousBufへ保持し、その元頂点に対する差分を8bitへ量子化する。一方Receiverは復元済み頂点へ量子化差分を累積加算する。エンコーダがReceiverと同じ復元状態を保持しないため、差分の量子化誤差は次のキーフレームまで蓄積する。floorによる切り捨ても負方向の偏りを生む。現在は30フレームごと（公称約0.5秒）にキーで位置を更新するため、長時間無制限にドリフトするのではなく、キー境界の補正が細かな跳ねとして見える可能性がある。

算術例として1軸の+0.001/-0.001を交互に29回符号化・復元すると、正確な0の初期キーに対して真値0.001、復元値約-0.006714、誤差約-0.007714となる。これは現行シェーダー式のCPUシミュレーションであり、KAGURAの実測誤差ではない。`Logs/iOSKagura/delta-quantization-analysis.json`。既存のCPU/GPU一致テストはデコーダ同士の一致で、元の頂点に対する符号化損失の否定には使えない。

次の切り分けは、同一モーションの元頂点と復元頂点を比較し、キー境界の誤差変化を測定すること。対策候補はSenderにも量子化後の復元頂点を保持し、それを基準に次の差分を作る方式（キーの復元誤差も含める）。丸め方式だけの変更では累積そのものは解消しない。キャプチャ間隔の乱れも別に残っており、量子化が今回の見た目の主因かは未確定。この調査ではコーデックや実行中の設定は変更していない。
